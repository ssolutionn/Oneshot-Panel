## Начало вето

В обеих формах создания по умолчанию монетка. Дополнительные варианты —
первая или вторая команда выбирает, кто банит первым. Это назначение права
выбора, а не заранее сделанный бан.

Новые комнаты используют версию 3: дополнительный байт задаёт монетку
или назначенную команду. Подписи ходов и heartbeat связывают формат,
таймер, команды, отпечатки ключей и настройку старта. Проверочный кеш тоже
зависит от комнаты. Изменение настройки в ссылке не переносит старые подписи.
Назначенная команда подписывает order первым ходом; таймер начинается
с этого выбора. Интерфейс и сообщения не называют назначение выигранной
монеткой. Перезапуск комнаты сохраняет режим старта.

Версия 2 и её прежние подписи продолжают приниматься. Действующие ссылки
не меняются. Читаемые зашифрованные ссылки несут тот же новый формат
без изменения серверного API.

## Фото игроков: варианты

| Вариант | Как работает | Ограничение |
|---|---|---|
| Локальный каталог в репозитории | Свои PNG/WebP/JPG кладём в assets/players; одна запись связывает команду, ник, aliases и file. Карточки и готовые OBS-пакеты уже используют этот каталог. | Добавление и публикация требуют доступа к репозиторию. Подходит для первого LAN. |
| Загрузка в панели → Cloudflare R2 | Админ выбирает команду/игрока, загружает и кадрирует фото, видит карточку. Файл и привязка хранятся централизованно; OBS читает изображение через домен панели. | Нужно реализовать защищённую запись, R2 и обработку изображений. Рекомендуемый постоянный вариант. |
| Импорт из общего хранилища | Фото лежат в общей папке/медиатеке; панель импортирует их в свой каталог. | Нужно согласовать источник и доступ. Прямые ссылки Drive и сторонние hotlink не дают надёжного показа в OBS. |

Для каталога не нужен HLTV ID. Пример записи:

    {"team":"LAN Team","nick":"Player","aliases":["OtherNick"],
     "source":"local","file":"lan-team-player.webp"}

Нужно обновлять существующую запись этой пары, а не создавать дубликат:
при неоднозначном совпадении карточка намеренно показывает заглушку.

Для будущей загрузки через панель:

- Запись доступна только админам, например через Cloudflare Access;
  ключ R2 не отправляется браузеру. Отдельно ограничиваются объём, размер
  и частота загрузок.
- Чтение карточек и изображений доступно OBS без входа в аккаунт.
  Same-origin маршрут /media/players/... сохраняет текущую CSP.
- После загрузки — проверка формата/размеров, нормализация в WebP/PNG,
  удаление EXIF, предпросмотр кадрирования. Исходник и готовая версия
  разделены. Прозрачный фон используется, когда он есть в исходном фото.
- Привязка к устойчивой личности команды/игрока, версия изображения и
  приоритет ручного фото над HLTV. Привязка обновляется атомарно после
  сохранения файла; неудачная загрузка сохраняет прежнее фото.

## Кадрирование камер

Подтверждённый размер — 1296×972 по центру холста 1920×1080:
X=312, Y=54. Он выбран по умолчанию; видео заполняет рамку, обрезая края.
Варианты 4:3 на всю высоту и весь холст доступны отдельным выбором.

«Кадр» под ником открывает предпросмотр без звука. Есть поворот на
0/90/180/270°, сдвиг области показа и сброс. Изменения сохраняются
для игрока в текущем браузере и попадают в следующий JSON/отправку OBS;
положение слота не является ключом. Сдвиг и поворот предпросмотра
не переподключают видео. CARD остаётся без поворота в той же рамке.

JSON и live OBS используют общую геометрию. Для поворота 90/270°
меняются размеры browser source и координаты его угла. Матрица не меняется.
Новая команда моста apply-camera позволяет старому доку отклонить её до
изменений и показать инструкцию обновления. Обновлённый док принимает
старую команду apply с её прежней геометрией, чтобы обновление дока
не меняло камеры старой панели.

Использованы существующие интерфейсы VDO: cover, b64css и iframe-сообщение
style. Их наличие проверено в upstream VDO.Ninja,
коммит 22158096222de4de1e6ef75a020d738374b4a3ea; код провайдера не копировался.
Автоматически определить верх изображения по его пропорциям нельзя:
для бокового видео оператор выбирает поворот в редакторе.

## Что ещё требует решения

- У двух устройств одного капитана нет общей блокировки подписи:
  Web Lock защищает только вкладки одного браузера. Конфликт двух
  подписанных ходов обнаруживается; централизованная аренда капитанского
  места требует отдельного протокола.
- VDO по-прежнему выбран по умолчанию в формах. Созданную VDO-комнату
  нельзя незаметно перевести на HTTP: потребуются новые ссылки или
  специально согласованный протокол миграции. Камеры также остаются VDO.
- API коротких ссылок разрешает публичное создание неизменяемых записей
  без срока удаления. Данные зашифрованы, но перед широким использованием
  нужны лимиты создания/квоты Cloudflare и решение об админской записи.
  Длительность хранения действующих ссылок не следует менять незаметно.
- FACEIT может не отдавать текущие раунды или отдавать их с задержкой.
  Новый интерфейс показывает это; гарантировать live-раунды сверх
  возможностей API нельзя.
